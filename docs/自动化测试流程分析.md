# 自动化测试基本流程 — 分析

> 一句话：自动化测试做不到 100% 覆盖，只能尽可能提高覆盖率；先做正向用例，再多轮筛选出反向用例。

## 一、七步流程图

```
                         ┌──────────────────────────────┐
                         │  覆盖率缺口（每月复盘反哺）   │
                         └───────────────▲──────────────┘
                                         │
┌──────────────┐  目标与范围  ┌──────────────┐  计划约束   ┌──────────────┐
│ ① 分析测试需求 │ ───────────▶ │ ② 制订测试计划 │ ──────────▶ │ ③ 设计测试用例 │
│ 覆盖率目标    │              │ 对象/目的/方法 │             │ 前置·步骤·预期 │
│ 正/反向边界   │              │ 人/机/数据    │             │ 明确断言      │
└──────────────┘              └──────────────┘             └──────┬───────┘
                                                                  │ 用例
                                                                  ▼
                                                          ┌──────────────┐
                                                   并行 ──▶ │ ④ 搭建测试环境 │
                                                          │ 部署·硬件     │
                                                          │ 工具·网络     │
                                                          └──────┬───────┘
                                                                 │ 环境是前提
                                                                 ▼
┌──────────────┐   执行结果   ┌──────────────┐          ┌──────────────┐
│ ⑥ 分析结果    │ ◀─────────── │ ⑤ 编写并执行脚本│ ◀──────── │              │
│ 归因：产品?   │              │ 框架→脚本→自检 │          └──────────────┘
│ 脚本? 环境?   │              └──────▲───────┘
└──────┬───────┘                     │
       │ 真缺陷                      │ 回归 / 需求偏离先改脚本
       ▼                             │
┌──────────────┐                     │
│ ⑦ 跟踪测试 Bug│ ────────────────────┘
│ 修复→回归→闭环 │
└──────────────┘
        │
        └──▶ 覆盖率缺口 → 回到 ①
```

要点：**两条虚线是质量的关键**——⑤ 的自纠环（脚本自身要正确）和 ⑥→⑤ 的回查环（非产品问题不能当 Bug 提）。

## 二、逐步分析

| 步骤 | 要解决的问题 | 输入 → 产出 | 门槛（做到什么程度算过） |
|---|---|---|---|
| ① 分析测试需求 | 测到什么程度？测哪些？ | 需求/评审结论 → 覆盖率目标、正/反向清单、自动化粒度 | 覆盖率量化，正/反向边界清晰 |
| ② 制订测试计划 | 为什么测、怎么测、谁测、用什么测 | 目标清单 → 对象/目的/内容/方法、人力与资源、可跟踪进度 | 计划进管理工具，有责任人和排期 |
| ③ 设计测试用例 | 用例能不能被脚本跑、能不能判定 | 计划 → 前置、步骤、数据、预期、断言 | 每条用例都有可断言的预期结果 |
| ④ 搭建测试环境 | 环境稳不稳、能否复现 | 资源 → 部署、硬件、工具、网络 | 可一键/脚本化重建 |
| ⑤ 编写并执行脚本 | 脚本本身对不对 | 用例 + 环境 → 可重复脚本、结果报告 | 在正确版本通过、缺陷版本失败 |
| ⑥ 分析结果、记录问题 | 红了之后是谁的问题 | 结果 → 缺陷单 或 脚本/环境修正 | 每个失败都有归因 |
| ⑦ 跟踪测试 Bug | 缺陷闭环，需求变了脚本要跟 | 缺陷单 → 闭环状态、回归版本 | 缺陷关闭且回归通过、脚本与需求一致 |

### 关键判断

1. **① 是定方向的，不是读书**。反向用例「大多靠分析筛选」，所以第 1 步就要产出正/反向清单，否则第 3 步只能靠拍脑袋。
2. **② 是资源匹配**，不只是写文档。人员、硬件、数据任何一项不到位，后面的自动执行都会卡住。
3. **③ 的检验标准是「可断言」**，不是「写完了」。预期结果含糊 = 失败时无法定位。
4. **④ 与 ③ 并行**，原文明确「用户在设计工作开展的同时即可搭建环境」。
5. **⑤ 最容易漏的是自检**：先证明脚本能在正确版本通过、在缺陷版本失败，否则脚本 bug 会被当成产品 bug。
6. **⑥ 是分诊（triage）**：真缺陷 → 提给开发；否则回查脚本或环境。这一步做不好，自动化结果就没人信。
7. **⑦ 是闭环**：修复后回归；若修改方案与客户一致但偏离原需求，**回归前先改脚本**，否则回归结论是错的。

## 三、映射到本插件工作台

| 流程步骤 | 插件里的落点 | 状态 |
|---|---|---|
| ① 分析需求 | 阶段备注 + 覆盖率目标 | 备注可写，**覆盖率目标目前只有展示/默认 85%，没有编辑入口** |
| ② 测试计划 | 阶段备注 | 仅备注 |
| ③ 设计用例 | 正向/反向分桶、设计方法、前置、步骤、预期、执行结论 | 完整可编辑 |
| ④ 环境 | 阶段备注 | 仅备注 |
| ⑤ 脚本与执行 | 阶段备注 | 仅备注 |
| ⑥ 结果分析 | 用例的「执行结果」+ 缺陷录入 | 部分支持 |
| ⑦ Bug 跟踪 | 缺陷状态机（待处理→处理中→已解决→回归中→已关闭）+ 关联用例 | 完整 |

**差距清单（按优先级）**
1. 覆盖率目标没有编辑入口（第 1 步的核心指标）；自动化粒度只是文字备注，没有结构化字段。
2. 第 2/4/5 步只有备注，没有结构化字段（测试对象、环境清单、脚本仓库路径等）。
3. 第 5 步缺「脚本自检」标记（在正确版本通过 / 缺陷版本失败），而那正是最常见的坑。
4. 第 6 步缺「失败归因」字段（产品 / 脚本 / 环境），直接对应原文的分诊要求。
5. 第 7 步缺「回归结果」和「需求偏离已同步脚本」的勾选，闭环不完整。

## 四、结论

七步里真正决定自动化成败的是四个**回流动作**：
- ①→③ 的正反向筛选（少了它，用例全压在主流程）
- ⑤→⑤ 的脚本自检（少了它，红色的信噪比崩掉）
- ⑥→⑤ 的归因回查（少了它，脚本问题当产品 Bug 上报）
- ⑦→⑤ 的需求偏离改脚本（少了它，回归给出错误结论）

工作台目前把 ③ 和 ⑦ 做实体化，①⑥ 部分结构化，②④⑤ 还停留在备注，建议按上面差距清单补齐。
